# 项目文档重组设计

## 1. 目标

把当前分散在 `README.md`、部署手册、设计规格和实施计划中的说明，整理成一套适合正式发布的中文项目文档。

整理后的文档必须满足以下目标：

- 普通用户、服务器管理员和开发维护者都能从同一个入口找到自己的阅读路径。
- 正式说明只有一个权威正文，部署命令、配置说明和运维流程不在多个文件中重复维护。
- 第一次接触项目、会使用基本终端但不熟悉 Docker 的管理员，也能独立完成部署、验收、备份、恢复和升级。
- 历史设计规格和实施计划继续保留，但与正式用户文档隔离。
- 文档内容必须与仓库中的代码、脚本、配置文件和实际支持边界一致。

## 2. 当前问题

现有文档存在以下结构性问题：

- `README.md` 同时承担英文项目介绍、本地启动、业务流程、配置和个人 API 说明，缺少清晰的中文发布入口。
- `docs/deployment/linux-docker.md` 虽然包含大量部署内容，但与 README 相互割裂，用户不知道应先读哪一份。
- `docs/superpowers/specs` 和 `docs/superpowers/plans` 中混有开发过程资料，发布用户容易把历史设计或实施步骤误认为当前操作手册。
- 普通用户、管理员和开发者的内容没有分层，阅读者需要自行判断哪些章节与自己有关。
- 部分说明只有结论或命令，缺少前置条件、预期结果、验证方法和失败处理。

## 3. 采用方案

采用“简洁项目首页 + 一本中文主手册 + 内部资料归档”的结构：

```text
README.md
docs/
├── PROJECT-MANUAL.md
└── internal/
    ├── README.md
    ├── specs/
    └── plans/
```

各文件职责如下：

- `README.md`：中文项目首页，只包含项目定位、核心能力、正式支持边界、快速本地体验、完整手册入口和基本验证命令。
- `docs/PROJECT-MANUAL.md`：唯一正式《完整项目手册》，覆盖使用、部署、运维和开发维护。
- `docs/internal/README.md`：说明内部资料的用途、历史属性和阅读限制。
- `docs/internal/specs`：保留设计决策和经过确认的规格。
- `docs/internal/plans`：保留历史实施计划，明确其中命令和文件状态不构成当前发布说明。

不采用以下方案：

- 不按角色拆成三套手册，因为部署、配置、API 和故障处理会产生重复内容，后续容易不一致。
- 不把全部正文放进 README，因为超长首页不便浏览，也不利于维护。

## 4. 读者与阅读路径

主手册开头必须提供三条明确路径：

### 4.1 普通用户

登录系统，创建或导入脚本，管理素材变量，编辑分镜，确认生成，查看结果，返修镜头，恢复历史版本，并配置当前会话的个人 API。

### 4.2 服务器管理员

确认支持边界，准备 Linux 和 Docker 环境，设置生产变量，部署 HTTPS 服务，完成首次验收，执行日常运维、备份恢复、升级回滚和故障排查。

### 4.3 开发维护者

准备本地开发环境，理解架构和数据目录，运行测试与构建，核对配置和接口，并执行发布前检查。

## 5. 主手册章节

`docs/PROJECT-MANUAL.md` 按以下顺序组织：

1. 文档说明与三类读者路线。
2. 项目能力、限制和正式支持范围。
3. 系统架构、网络边界、数据流与目录结构。
4. 五分钟本地体验。
5. 普通用户完整操作流程。
6. 个人 API 设置、隐私边界和常见错误。
7. 正式服务器部署前的决策与检查表。
8. Linux、Docker、网络、防火墙和服务器账号准备。
9. 生产环境变量逐项说明。
10. Docker Compose 首次部署完整流程。
11. Caddy 内部 CA 与客户端证书信任。
12. 首次上线验收。
13. 日常运维和资源检查。
14. 数据、备份、自动备份、恢复演练和灾难恢复。
15. 升级、回滚和版本记录。
16. 按现象组织的故障排查。
17. 安全边界与发布检查清单。
18. 本地开发、代码结构、测试和构建。
19. 配置项、端口、路径、脚本、接口和状态码速查表。
20. 运维、变更和故障记录模板。
21. 术语表与常见问题。

长章节使用稳定的小节标题和页内目录，避免仅靠连续正文表达层级。

## 6. 操作章节写法

凡是要求读者执行操作的章节，统一采用以下信息顺序：

1. 适用场景。
2. 前置条件。
3. 操作步骤。
4. 预期结果。
5. 验证方法。
6. 失败处理。
7. 安全提醒。

命令必须满足以下规则：

- 命令块注明执行平台，例如 Linux Bash 或 Windows PowerShell。
- 说明命令应在哪个目录、以哪个账号执行。
- 占位值使用统一格式，并在命令前解释如何替换。
- 高风险命令在执行前说明影响对象、必要备份和回退方式。
- 同一项操作只保留一套权威命令；其他章节通过链接引用。
- 每个关键步骤给出可观察的成功结果，不能只写“执行以下命令”。

## 7. 内容来源与一致性

正式手册以当前仓库内容为事实来源，至少核对以下文件和实现：

- `package.json` 中的运行、维护、测试和构建脚本。
- `Dockerfile`、`compose.yaml`、Caddy 配置和容器健康检查。
- `.env.example` 中的环境变量、默认值和注释。
- 部署、备份和恢复脚本的参数、安全校验及退出行为。
- 服务端运行时配置校验、认证、会话 API 设置和就绪检查。
- SQLite 数据目录、输出目录、上传目录和持久化挂载。
- 客户端实际支持的用户操作、材料类型和返修行为。

当旧文档与代码不一致时，以经过测试的当前实现为准，并修正文档；不通过文档整理顺带改变业务行为。

## 8. 迁移规则

- 将 `docs/deployment/linux-docker.md` 的有效内容合并进 `docs/PROJECT-MANUAL.md`。
- 主手册形成后删除旧部署正文，避免出现第二套权威部署步骤。
- 将 `docs/superpowers/specs` 下的历史规格移动到 `docs/internal/specs`。
- 将 `docs/superpowers/plans` 下的历史计划移动到 `docs/internal/plans`。
- 更新仓库内所有受影响的相对链接。
- 不改写历史规格和计划的正文，只调整位置；必要的历史说明统一写在 `docs/internal/README.md`。
- Git 移动应保持内容可追溯，避免无意义格式化历史文件。

## 9. 安全与支持边界

主手册必须明确以下正式支持边界：

- 正式部署面向受信任局域网内的多人使用。
- 正式拓扑为一台 Linux 主机、一个应用容器和一个 Caddy 容器。
- SQLite 数据目录不能由多个应用副本并发写入。
- 正式访问使用 Caddy 内部 HTTPS，不把应用 HTTP 端口直接暴露给局域网用户。
- 不通过路由器端口转发把服务发布到公网。
- 个人 API 密钥仅存在于服务端会话内存，不写入浏览器存储、数据库、任务记录或生成文件。
- 恢复、升级、回滚和卸载前必须验证目标目录并保留可恢复备份。

超出这些边界的公网部署、多节点高可用、外部身份系统和集中式密钥管理不纳入本次文档范围。

## 10. 验收标准

文档重组完成后必须满足以下条件：

- 仓库根目录存在清晰的中文 README，且能在两次点击内进入任意正式章节。
- 正式用户只需阅读 `README.md` 和 `docs/PROJECT-MANUAL.md`，不依赖内部资料。
- 不存在第二份重复的正式部署手册。
- 主手册覆盖本设计第 5 节列出的全部章节，没有空白占位或待补内容。
- 环境变量、端口、目录、脚本和命令与当前仓库一致。
- 所有仓库内相对链接、标题锚点和示例路径有效。
- Markdown 标题层级连续，代码块闭合，目录与章节一致。
- `npm test` 和 `npm run build` 通过，确认文档移动没有破坏测试或构建引用。
- `git diff --check` 通过，仓库不存在意外格式问题。

## 11. 非目标

本次整理不包含以下工作：

- 不修改应用功能、接口行为或用户界面。
- 不增加公网部署、多应用副本或 Kubernetes 方案。
- 不把历史规格和实施计划改写成当前说明。
- 不提供与当前代码无关的通用 Linux 或 Docker 教程。
- 不承诺尚未由仓库实现和测试的能力。
