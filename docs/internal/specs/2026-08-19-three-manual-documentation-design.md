# 三份正式手册重组设计

## 1. 目标

把当前混合普通用户、开发维护者和服务器管理员内容的 `docs/PROJECT-MANUAL.md` 重组为三份职责明确的正式手册，并保留仓库根目录 `README.md` 作为简要说明和统一入口。

完成后的正式文档只有四个入口：

```text
README.md
docs/USER-GUIDE.md
docs/DEVELOPMENT.md
docs/DEPLOYMENT.md
```

`docs/internal/` 继续保存历史设计规格和实施计划，不属于当前产品说明。

## 2. 设计原则

### 2.1 按受众分工

- 普通使用者只需要阅读使用说明，不应先理解 Docker、SQLite 或源代码。
- 开发维护者需要理解系统结构、实现边界、配置契约、测试和发布规则。
- 服务器管理员需要完成局域网生产部署、日常运维、备份恢复和升级回滚。
- 第一次接触项目的人从 README 判断用途、支持范围和应该阅读哪份手册。

### 2.2 一个事实只有一个详细来源

同一主题只在一份手册中完整解释，其他手册使用简短说明和相对链接引用。例如：

- 用户如何填写个人 API 设置在 `USER-GUIDE.md`；服务器默认 API 环境变量在 `DEPLOYMENT.md`；设置解析、会话隔离和接口契约在 `DEVELOPMENT.md`。
- 用户如何选择“融入画面”或“原样展示”在 `USER-GUIDE.md`；素材变量、供应商请求和 ffmpeg 叠加实现放在 `DEVELOPMENT.md`；外部供应商访问素材所需的生产 URL 配置放在 `DEPLOYMENT.md`。
- 用户看到错误时如何处理在 `USER-GUIDE.md`；代码调试方法在 `DEVELOPMENT.md`；容器、证书、备份和服务器故障在 `DEPLOYMENT.md`。

### 2.3 不保留过时总手册

新手册完成后删除 `docs/PROJECT-MANUAL.md`。不建立内容重复的总手册、摘要副本或兼容占位页，避免搜索结果继续把读者带到旧结构。

历史 `docs/internal/` 文件可以保留当时的旧路径和命令作为历史记录，但 `docs/internal/README.md` 必须明确指向新的正式文档入口。

## 3. README 简要说明

`README.md` 控制为适合仓库首页快速浏览的长度，包含：

1. 项目一句话定位和局域网适用范围。
2. 核心能力，包括剧本、分镜、素材、视频生成、返修和会话级 API 设置。
3. 正式支持与明确不支持的部署范围。
4. 本地五分钟启动和生产构建命令。
5. 三份正式手册的入口和各自适用人群。
6. 开发验证命令。
7. 内容审核与版权责任提醒。

README 不承载完整用户步骤、全部环境变量、接口表、备份恢复命令或代码结构说明。

## 4. 详细使用说明

新建 `docs/USER-GUIDE.md`，面向实际操作工作台的普通用户。章节顺序遵循完整任务流程：

1. 文档适用范围和开始前准备。
2. 登录、退出和页面布局。
3. 创建视频：主题、关键词、风格、时长、画幅和生成方式。
4. 导入 TXT、Markdown、DOCX 剧本。
5. 上传图片、视频、音频、CSV 和 XLSX。
6. 生成并检查剧本和分镜。
7. 编辑短标题、旁白、画面设计、时长和顺序。
8. 素材变量与剧本融合：添加绑定、融入画面、原样展示、声音、数据图表、位置和时间范围。
9. 个人脚本 API 与视频 API 设置、密钥生命周期和任务设置快照。
10. 确认生成、进度、结果下载和反馈。
11. 重新合成、编辑已有镜头、重新生成镜头和历史版本恢复。
12. 常见用户错误、术语和问答。

每个操作章节至少说明：入口位置、操作步骤、成功表现、常见失败和安全提醒。部署命令、源代码和管理员环境变量不进入正文。

## 5. 开发技术文档

新建 `docs/DEVELOPMENT.md`，面向接手代码、修改功能和准备发布的开发者。章节包括：

1. 技术栈、运行模式和支持边界。
2. 系统架构、数据流、信任边界和单进程 SQLite 约束。
3. 仓库目录、前端组件、服务端模块和共享类型职责。
4. 本地开发环境、依赖安装、启动、构建和维护命令。
5. 运行时配置解析、安全校验和新增配置的同步位置。
6. 数据模型、SQLite、素材存储、输出和修订版本。
7. 认证、会话级 API 设置、写请求保护和密钥生命周期。
8. 剧本规划、分镜确认、任务队列和生成流程。
9. 素材融合技术：`@变量` 解析、结构化绑定、预检、Seedance reference、首尾帧、精确叠加、数据图表和 ffmpeg 合成。
10. HTTP 接口、状态码和主要请求数据。
11. 测试布局、视觉 QA、构建和发布验证。
12. 提交范围、忽略规则、文档同步和代码库整洁要求。

开发文档可以引用部署手册中的生产拓扑和环境变量值，但重点解释代码如何读取和使用这些配置，不重复完整部署步骤。

## 6. 部署运维手册

新建 `docs/DEPLOYMENT.md`，继承现有手册中已经验证的生产部署内容，并重新编号。章节包括：

1. 支持拓扑、非目标和部署前决策。
2. Linux 主机、CPU 架构、时间、磁盘、固定 IP 和 DNS 准备。
3. Docker Compose、目录、UID/GID 和防火墙准备。
4. 全部生产环境变量、默认值、必填条件和安全约束。
5. Caddy 内部 HTTPS 和各客户端 CA 信任。
6. 首次构建、启动、健康检查和上线验收。
7. 登录、日志、状态检查和日常运维。
8. 数据布局、完整备份、校验、第二份副本、定时任务和恢复演练。
9. 升级、镜像记录、回滚和数据兼容性。
10. 服务器、容器、readiness、证书、供应商网络和磁盘故障排查。
11. 安全边界、停止、保留数据卸载和完全销毁。
12. 发布、备份、恢复、证书和故障记录模板。

生产环境变量、端口、路径和部署脚本速查保留在该文档。HTTP 接口实现细节移到开发文档；普通用户操作仅保留上线验收所需的冒烟步骤，并链接使用说明。

## 7. 现有章节迁移

当前 `PROJECT-MANUAL.md` 的内容按以下原则迁移：

| 现有章节 | 目标文档 |
| --- | --- |
| 1 文档说明与阅读路线 | README 和三份手册各自前言 |
| 2 项目能力、限制与支持范围 | README；详细技术边界进入 DEVELOPMENT；部署边界进入 DEPLOYMENT |
| 3 系统架构、网络边界与目录 | DEVELOPMENT；生产宿主机目录进入 DEPLOYMENT |
| 4 五分钟本地体验 | README 和 DEVELOPMENT |
| 5 普通用户完整操作 | USER-GUIDE |
| 6 个人 API 设置 | USER-GUIDE；实现边界进入 DEVELOPMENT；服务器默认配置进入 DEPLOYMENT |
| 7-15 部署、运维、备份和升级 | DEPLOYMENT |
| 16 故障排查 | 按用户、代码、服务器问题分入三份手册 |
| 17 安全边界、发布检查与卸载 | DEPLOYMENT；代码发布检查进入 DEVELOPMENT |
| 18 本地开发与发布维护 | DEVELOPMENT |
| 19 配置、端口、路径、命令与接口速查 | 配置/端口/路径/部署脚本进入 DEPLOYMENT；接口进入 DEVELOPMENT |

迁移不是简单剪切：每份文档需要独立标题、适用对象、目录、前置条件、相关文档链接和完整阅读顺序。

## 8. 链接与权威关系

README 的文档入口固定为：

```text
普通用户 -> docs/USER-GUIDE.md
开发维护 -> docs/DEVELOPMENT.md
部署运维 -> docs/DEPLOYMENT.md
历史追溯 -> docs/internal/README.md
```

三份手册开头互相链接，并声明自己的权威范围。所有正式文档不得链接 `docs/internal/specs/` 或 `docs/internal/plans/` 作为当前操作依据。

代码中的路径引用、README 锚点、内部资料说明和文档检查器全部更新。仓库中不再出现指向 `docs/PROJECT-MANUAL.md` 的当前链接；内部历史正文不重写。

## 9. 自动检查

更新 `scripts/check-docs.mjs`：

- 必须存在 `README.md`、`docs/USER-GUIDE.md`、`docs/DEVELOPMENT.md`、`docs/DEPLOYMENT.md` 和 `docs/internal/README.md`。
- 禁止重新出现 `docs/PROJECT-MANUAL.md`、旧部署文档路径和 `docs/superpowers/`。
- 对 README 和三份正式手册执行标题层级、代码围栏、本地链接和标题锚点检查。
- 对 README 和三份正式手册扫描未完成占位内容。
- 历史内部资料仍检查链接可达性，但不强制改写历史标题层级。

检查器只使用 Node.js 标准库，不增加依赖。

## 10. 验收标准

1. README 可以在数分钟内说明项目、支持范围、启动方式和三份手册入口。
2. 用户仅阅读 `USER-GUIDE.md` 可以完成从登录到生成、素材融合、返修和下载。
3. 开发者仅阅读 `DEVELOPMENT.md` 可以理解架构、配置、核心流程、接口、测试、构建和提交规则。
4. 管理员仅阅读 `DEPLOYMENT.md` 可以完成生产准备、部署、验收、备份恢复、升级回滚和故障处理。
5. 原 `PROJECT-MANUAL.md` 的正式信息都有明确归属，没有因拆分丢失环境变量、命令、安全约束或操作步骤。
6. 三份手册之间没有大段重复，交叉主题使用链接连接。
7. 当前代码库中不存在指向已删除手册的正式链接。
8. `npm run docs:check`、`npm test`、`npm run build` 和 `npm run verify` 通过。
9. `git diff --check` 通过，最终工作树干净。
10. 不提交 `dist/`、日志、数据库、运行数据、截图或其他中间生成文件。

## 11. 非目标

- 不修改业务逻辑、界面、接口、运行配置含义或部署拓扑。
- 不把文档转换为网站、PDF、Word 或多语言版本。
- 不重写 `docs/internal/` 中的历史规格和计划正文。
- 不引入文档生成器或第三方 Markdown 工具。
